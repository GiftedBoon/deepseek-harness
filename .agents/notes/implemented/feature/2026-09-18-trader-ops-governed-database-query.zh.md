# Agent Note: Trader Ops 受控数据库查询

Status: implemented

[English](2026-09-18-trader-ops-governed-database-query.md) | 中文

## 问题

Trader Ops 需要检查 Microsoft SQL Server 和 ClickHouse 中的运维数据，但现有 Agent 只能访问面向命令的 bssh_ops 工具。若直接向 Agent 提供数据库查询 CLI 或不受限的 SQL 传输，会绕过团队使用所需的部署工具策略、集中审计记录、结果限制和稳定错误处理。单独部署 MCP 又会重复 bssh_ops 已经拥有的身份验证、服务管理和 Harness 连接配置。

## 决策

现有 `bssh-ops-remote` MCP 连接暴露四个数据库工具：连接发现、表发现、schema 检查和 SQL 查询执行。MCP 进程继续作为轻量的认证 HTTP 适配器；data-analysis 后端负责连接别名、SQL 校验、执行限制、并发控制、响应整形和查询审计记录。连接 allowlist 缺失或为空时不会暴露任何数据库。Harness 通过部署策略准确放行这四个工具名，并将工具超时设为 75 秒。

`database-query` Skill 独立于面向命令的 bssh_ops Skill，负责 Agent 工作流。它要求先发现连接和 schema，再构造查询；要求 Agent 从有界聚合或样本查询开始；还要求向用户报告查询 id 和截断状态。该 Skill 不能覆盖后端拒绝，也不能获取未注册的连接。

`pre-open-status-check` Skill 是复用同一组工具的确定性业务流程。它检查 `ProductionMonitorData.CreateTime` 最大值对应的行，把空批次视为无法判断，只在每个 `PnLratio` 都精确等于零时报告成功，并且只为非零或 NULL 值获取产品明细。它报告快照时间但不虚构时效阈值，也不推断失败检查究竟意味着处理仍在进行还是未开启产品异常。

后端只接受一条 SQL 查询，使用对应数据库方言解析，拒绝非查询语句和危险的外部数据源函数，限制跨数据库访问，并应用最外层行数上限。独立的有界 SQLAlchemy 连接池以及全局和逐连接信号量，把 Agent 流量与现有应用连接池隔离。审计行记录身份、连接、规范化 SQL 哈希、引用表、耗时、状态、行数、字节数和稳定错误码，但不存储原始 SQL 或返回数据。

连接层目前复用部署中已有的 SQL Server 和 ClickHouse 凭据。因此，应用层校验提供当前的写入防护，而数据库原生只读账号仍是独立的加固步骤。

## 考虑过的替代方案

**部署独立的数据库 MCP 服务。** 拒绝，因为这会重复现有 API key 边界、进程监管、健康检查和 Harness 连接配置，却不会形成更强的授权边界。复用现有 MCP namespace 保留单一运维入口，同时由后端在内部隔离查询执行。

**让 Skill 直接调用 database-query CLI。** 拒绝，因为本地进程访问会使强制约束依赖 prompt 遵从，并分散审计和资源控制。所有数据库请求改为经过精确的 Harness 工具策略和后端校验。

**把工作流加入现有 bssh_ops Skill。** 拒绝，因为远程命令执行和分析 SQL 具有不同的发现、安全与结果解释规则。即使共用同一个 MCP 连接，独立 Skill 也能保持触发和操作指导聚焦。

**把每个业务检查都写入通用 database-query Skill。** 拒绝，因为业务专属表、固定 SQL、判定状态和报告措辞会让通用发现指导变得嘈杂且更容易误用。狭窄的业务 Skill 复用受控工具，同时拥有自身准确的指标语义。

**只依赖 SQL 文本前缀。** 拒绝，因为注释、公共表表达式、嵌套表达式和方言语法会使前缀检查可被绕过。后端校验解析后的语法树，并在无法确定解析或分类时封闭失败。

## 验证

策略测试覆盖语句分类、堆叠语句、隐藏在公共表表达式后的变更、外部数据源函数、跨数据库引用和行数上限重写。API 测试覆盖 Agent key 身份验证和稳定错误映射。MCP 注册检查验证全部四个工具，Trader Ops 策略验证则确认每个被引用工具都在所有部署环境中获准使用。

## 结果

- Trader Ops 可以通过现有的认证运维连接执行有界 SQL 分析，无需部署第二个 MCP。
- 数据库策略、资源限制和审计行为由一个后端统一负责，不会重复散落在 prompt 或 MCP wrapper 中。
- 在引入逐用户身份传递前，查询审计识别的是共享 Agent API 身份，而不是具体团队成员。
- 复用现有数据库凭据留下了纵深防御缺口：SQL 策略层以下的缺陷可能触达这些凭据已有的权限，因此在扩大使用范围前仍建议采用原生只读账号。
