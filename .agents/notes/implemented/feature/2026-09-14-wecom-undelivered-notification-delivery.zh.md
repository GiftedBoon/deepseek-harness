# Agent Note: 未投递的企业微信通知会保留到会话回来

Status: implemented

[English](2026-09-14-wecom-undelivered-notification-delivery.md) | 中文

## Problem

定时动作在到点那一刻通过主动 Markdown 发送汇报结果，而操作者不必在那一刻在线。提供方可能在该会话空闲时拒收这次发送。

在本改动之前，被拒收的记录按固定间隔重试，并在**达到 `maxOutboxAttempts` 后被删除**——按默认值是十次、间隔三十秒，约五分钟。入站消息则完全不触发任何投递尝试：触发点只有渠道启动、重连和间隔定时器。因此，在无人注视时到点的通知会在五分钟后被删除；一直无法投递的通知，只有在操作者恰好在某次重试仍挂起时写来消息才会出现。

有两个缺陷掩盖了原因。SDK 拒收回复时 reject 的是回执帧，而帧里的 `errcode` 与 `errmsg` 是提供方拒收原因的唯一陈述；运行时用 `errorChain` 渲染该帧，而它会把非 `Error` 对象字符串化，于是 journal 里记下的是 `[object Object]`。此外，一次失败尝试在不是最后一次时不产生任何日志，五分钟的连续拒收因此完全不可见。

## Decision

`drainOutbox` 把周期性重试与"会话在线时投递"分开，并且在到达 `outboxRetentionMs` 之前不删除任何记录。

| 触发点 | 范围 | 是否重试已耗尽的记录 |
|---|---|---|
| 渠道启动、SDK 认证成功 | 全部记录 | 是 |
| 间隔定时器（`outboxRetryIntervalMs`） | 全部记录 | 否 |
| 记录入队 | 仅该 target | 是 |
| 某会话准入了一条入站消息 | 仅该会话的 target | 是 |

达到 `maxOutboxAttempts` 的记录不再被定时器重试，转而等待所属会话写来消息，届时立即投递。记录只会因投递成功或到达 `outboxRetentionMs` 而被删除，后者默认七天，用于约束增长。周期性那一遍同时清理过期记录。

每次失败尝试都会记录尝试次数与提供方诊断。transport 适配器把被 reject 的 SDK 帧转成一条点名 `errcode` 与 `errmsg` 的 `Error`，使原因能穿过 `errorChain` 保留下来。目标与正文绝不进入日志，因为它们承载提供方身份与消息文本。

定时动作若已找不到会话路由，会记录一条 warning，而不是静默跳过通知。

## 投递触发点

排空串行在一条 promise 链上，因此入站触发的排空不会与定时器那一遍交错。入站排空不被 Agent turn 等待：turn 的答复走被动流，待发通知是一条独立的主动发送。因此主动发送失败只会推迟通知，绝不推迟回复。

按提供方 target 匹配而不是按会话键匹配，因为 outbox 记录存的是发送目标，而不是会话。一个会话的入站消息不会动到其他会话的记录，它们仍等自己的下一条消息。

## Alternatives considered

**保留"到达尝试上限即删除"。** 这正是产生缺陷的行为：该上限约束的是重试力度，而不是记录的价值；一条到点五分钟后被删除的通知无法找回。保留期把这个决定交给运维控制的时间。

**让定时器永久重试每一条记录。** 它什么也没约束，还会持续冲击一个已经拒收过的提供方。把周期性重试与会话在线投递分开，既保持力度有界，又保住了记录。

**把待发通知并进被动回复。** 被动回复是对刚到达那条消息的答复，并与它共享同一份 UTF-8 字节预算；把一条无关通知并进去会让两次交付混为一谈，并可能互相截断。主动发送也让通知保持独立可审计。

**为了解释失败而记录目标与正文。** 拒绝：本包从不记录已准入的提供方 id 或消息文本。提供方诊断本身已足以区分限流、请求格式错误与会话被拒。

**给 outbox 记录加一个状态字段。** 记录已经带有 `attempts`、`createdAt` 与 `updatedAt`，用尝试次数与 `maxOutboxAttempts` 的比较就能识别耗尽的记录。新增字段会要求 `channel_wecom` 域升版与迁移，而现有值已经表达了该信息。

## Consequences

换来的：在操作者不在时到点的通知，会在该会话下一次写来消息时投递，而不是五分钟后丢失；journal 会陈述发送失败的原因；未投递记录有了显式、可配置的保留期，而不是由重试算术隐含推导出来的一个。

代价：一条记录最长可在失去价值后再存活 `outboxRetentionMs` 那么久；有待发记录的会话在下一次写来消息时会多做一次主动发送尝试，其耗时由 SDK 的五秒回执超时约束；`maxOutboxAttempts` 不再约束保留期，决定何时放弃一条未投递通知的是 `outboxRetentionMs`。

渠道测试固定了四个触发点、保留期清理、逐次尝试诊断与入站仅限单一 target 的范围；transport 测试固定了 `errcode`/`errmsg` 的渲染。
